# 接口说明（增量）

> 这里只记**新增 / 行为有变化**的接口与表结构，从 v1.3.0 开始。其余接口以 `backend/src/routes/fin/*.js` 为准。
> 统一响应 `{ code, message, data }`：`code = 0` 成功；9002 参数 / 业务校验不通过；9003 无权限（HTTP 403）；9004 不存在或不在数据范围内。

## v1.3.0（2026-10-29）

### 一、录入助手草稿：落库、提交去重、状态持久化

#### `POST /api/fin/assistant/chat`（行为变化）

返回结构不变，`drafts[]` 里每张草稿多一个字段：

| 字段 | 说明 |
|---|---|
| `draftId` | 草稿 id（字符串）。草稿在 chat 返回前写入 `assistant_drafts`，后续查状态、提交都用它 |

#### `POST /api/fin/assistant/drafts/:id/submit`（新增）

「确认提交」。服务端带着当前用户的 token 代调对应模块现有的接口（新增 `POST /api/fin/{accounts|receivables|invoices|transactions}`，
修改 `PUT …/:targetId`），所以权限、数据范围、月结锁、审计、余额重算和直接调模块接口完全一致。

- 权限：`finance.view`，并且需要该草稿类型对应的 `*.manage`（否则 403）
- 只能提交**自己的**草稿；别人的草稿返回 9004
- 请求体：`{ payload? }` —— 用户在草稿卡上改过（如选了候选客户）就带上；不带则用落库时的 payload。
  草稿类型、新增 / 修改、修改目标 id **只认落库的**，请求体改不了
- 去重规则：
  1. **同一张草稿**提交成功后，再提交（任何时候）都返回第一次的结果，`duplicate: true`
  2. **不同草稿、内容相同**：指纹 = `sha256(类型 | 新增/修改 | 修改目标 id | 用户 id | 规范化 payload)`，
     规范化 = 键排序、去掉空值、字符串去首尾空格；不含时间戳。同指纹 **60 秒内**再提交 → 返回第一次的结果，`duplicate: true`，
     这张草稿也标成已提交（`duplicateOf` 指向第一次的草稿）；超过 60 秒视为新的一笔
  3. 并发：同一张草稿靠草稿锁（`locked_at` 条件更新）排队；同指纹靠 `assistant_submissions.fingerprint` 唯一索引，
     冲突后回查那一行——处理中就等它出结果（最多 15 秒），已成功就返回它的结果
  4. 模块接口拒绝（缺字段 / 越权 / 已结账 / 发票号重复…）时原样返回该错误（HTTP 状态与 code 不变），草稿不算已提交，指纹放开，改好后可再提交
- 成功响应 `data`：

| 字段 | 说明 |
|---|---|
| `draftId` | 草稿 id |
| `kind` / `mode` / `targetId` | 草稿类型 / `create` 或 `update` / 修改目标 id |
| `submitted` / `submittedAt` | 是否已提交 / 提交时间 |
| `id` | 业务记录 id（新增出来的或被修改的） |
| `code` | 业务编号：应收、流水为 `code`；发票为发票号；账户为账户名 |
| `duplicate` | `true` = 这次是重复提交，没有再写库，返回的是第一次的结果 |
| `originalId` | 重复时为第一次产生的业务记录 id（与 `id` 相同）；首次提交为 `null` |
| `originalDraftId` | 重复时为第一次提交的草稿 id |
| `record` | 仅首次提交：模块接口返回的完整记录 |

- 审计：每次提交记一行 `action = assistant.submit`（只记草稿 id、类型、业务 id、是否重复，不记金额）；模块自身的 `CREATE / UPDATE` 审计照旧

#### `GET /api/fin/assistant/drafts/:id`（新增）

查一张自己的草稿的提交状态，返回字段同上（不含 `duplicate` / `record`），另有 `duplicateOf`。抽屉关掉重开、草稿卡重建时用它把「已提交 · 编号 XXX」拉回来。

#### `GET /api/fin/assistant/drafts?ids=1,2,3`（新增）

批量查自己的草稿状态，最多 100 个；不存在或不是自己的 id 直接略过。返回 `{ list: [...] }`。

### 二、业务编号

编号格式不变（`TXN-YYYYMM-0001`、`AR-YYYY-0001`、`PAY-YYYYMM-0001`、`PR-YYYYMM-0001`、`AP/LN-YYYY-0001`、`EXP-YYYYMM-0001`），
分配方式改为 `code_sequences` 表在事务内加锁发号（见 `backend/src/lib/code.js`）：并发新增全部成功、编号连续不重复；
写入仍撞号时自动重取重试 3 次（指数退避），再失败返回「业务编号分配冲突，请稍后重试」。
内部转账一次取两个连续编号（转出、转入各一个）。编号可能出现空号（取了号但写入被拒），属正常。

### 三、错误信息

所有经 `wrap()` 的接口：Prisma 报错不再把原文（invocation、约束名）返回给前端，改为中文：
唯一约束冲突 → 9002（如「业务编号冲突，请重试」「该公司下发票号已存在」）；外键不存在 → 9002；记录不存在 → 9004；其它数据库错误 → 9001「服务器内部错误（数据库操作失败，已记录日志）」。

### 四、数据范围（行为变化）

以下接口补上了数据范围校验，与详情 / 列表同口径（范围与 `company_id` 取交集）：

| 接口 | 越权时 |
|---|---|
| `POST /api/fin/accounts/transfer` | 转出或转入账户不在范围内 → 9004「转出/转入账户不存在」 |
| `POST /api/fin/receivables/:id/receipt` | 应收不在范围内 → 9004；收款账户不在范围内 → 403；**收款账户不属于应收所在公司 → 9002**（所有角色） |
| `POST /api/fin/invoices/:id/link-transaction` | 发票或流水不在范围内 → 9004 |
| `POST /api/fin/transactions/batch` | 选中的流水有一笔不在范围内 → 403，有一笔不存在 → 9004；**整批都不改** |
| `POST /api/fin/transactions/import/preview`、`/import/commit` | 账户不在范围内 → 9004 |
| `GET /api/fin/transactions/import/batches` | 只列范围内公司的导入批次 |
| `POST /api/fin/invoices/import` | 公司不在范围内 → 403 |
| `GET /api/fin/ai/monthly-report` | 公司不在范围内 → 9004 |
| `GET /api/fin/ai/anomalies` | 重复发票检查的公司列表也与 `company_id` 取交集 |

另：`POST /api/fin/transactions` 不传 `bizType` 时按方向记为 `OTHER_IN` / `OTHER_OUT`（以前报数据库错误）。

> 发票与流水「解除关联」目前没有接口（只有关联），不在本次范围。

### 五、新表

用 `npx prisma db push` 建表（所有字段可空或有默认值，可直接在已有库上推）。

#### `code_sequences` 业务编号序列

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq_key` | varchar(32) PK | 编号前缀，如 `TXN-202610-`、`AR-2026-` |
| `seq_value` | int，默认 0 | 已发出的最大序号 |
| `updated_at` | datetime(3) | 最后取号时间 |

首次使用某前缀时自动从业务表里已有的最大编号续上，不需要手工初始化。

#### `assistant_drafts` 录入助手草稿

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | 即 `draftId` |
| `user_id` | bigint | 生成草稿的用户；只有本人能查、能提交 |
| `kind` | varchar(20) | `account` / `receivable` / `invoice` / `transaction` |
| `mode` | varchar(10) | `create` / `update` |
| `target_id` | bigint，可空 | 修改模式下要改的记录 id |
| `company_id` | bigint，可空 | 草稿里的公司（便于排查） |
| `payload` | json | 草稿内容；提交时更新为实际提交的内容 |
| `submitted_at` | datetime(3)，可空 | 提交成功时间（含被判为重复的） |
| `result_id` | varchar(32)，可空 | 产生 / 修改的业务记录 id |
| `result_code` | varchar(120)，可空 | 业务编号（应收 / 流水 code、发票号、账户名） |
| `duplicate_of` | bigint，可空 | 被判为重复时，第一次提交的草稿 id |
| `locked_at` | datetime(3)，可空 | 提交进行中的锁，防同一张草稿并发提交；超过 60 秒视为失效 |
| `created_at` / `updated_at` | datetime(3) | |

索引：`(user_id, created_at)`。

#### `assistant_submissions` 草稿提交指纹

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `fingerprint` | char(64) **唯一** | sha256 指纹，见上 |
| `user_id` | bigint | |
| `draft_id` | bigint | 本轮负责提交的草稿 |
| `kind` | varchar(20) | 草稿类型 |
| `status` | varchar(20) | `PENDING` 处理中 / `DONE` 成功 / `FAILED` 失败（可重试） |
| `result_id` / `result_code` | 可空 | 成功后的业务 id / 编号 |
| `claimed_at` | datetime(3) | 本轮提交开始时间，60 秒窗口从这里算；过期或失败的行被下一次提交原地接管 |
| `created_at` / `updated_at` | datetime(3) | |

索引：`fingerprint` 唯一、`user_id`。
